# Fail-closed artifact provenance and submission-readiness gates

This change adds a dependency-free verifier for the compact E19/E20 archives, freezes the submission claim/readiness state, and runs both checks before dependency installation in CI. The files consistently preserve the critical limitation that E19/E20 used unavailable, unreconstructible dirty source bytes, and the tagged final E-NL source fingerprint independently matches commit `2d0ee83`. The blocking problems are between the individually valid documents: readiness can become `go` by shedding gates, claim evidence is not matched to the verified archive, and provenance/acceptance classifications can be self-asserted.

Watch for: **High, confirmed** — deleting gates or changing their `required_for_submission` flags can produce a validated `go`; **High, confirmed** — E19/E20 evidence hashes and the explicit historical-source limitation are not cross-checked against `provenance_manifest.json`; **Medium, confirmed** — `clean_git_source` accepts a nonexistent commit and unproved source digest; **Medium, confirmed** — evaluation `passed` and `accepted_primary_outputs` are not tied to checks or the restricted claim; **Low, likely** — the provenance generation timestamp predates both frozen studies.

**Verdict**: NEEDS_CHANGES

## High-level view

The release verifier establishes a strong byte-level boundary, including canonical path confinement, duplicate rejection, sidecar/hash agreement, and optional Git tracking. Its semantic boundary stops short of proving a clean-source classification or binding evaluation acceptance to the restricted endpoint set (**confirmed**).

The readiness validator computes readiness from whichever gates are present and trusts their mutable required/optional flags. Mandatory blockers can therefore disappear without invalidating the manifest (**confirmed**).

The claim set and archive provenance are checked independently. Digest-shaped evidence and duplicated historical-source flags need not describe the archive that CI verifies, and the top-level E19/E20 limitation is outside validation (**confirmed**).

The public E-NL entry point rejects non-lockstep or inexact-response evaluation before output creation, with dedicated tests for both guards and existing smoke coverage for pin, source, protocol, and byte tampering. The remaining coverage gaps are in cross-document integrity, not guard ordering.

## Readiness can become `go` after mandatory gates disappear — High (**confirmed**)

`scripts/check_submission_readiness.py:178-236` derives `computed_ready` solely from supplied `gates`, requires only `claims_frozen` and `official_2027_requirements_sourced`, and trusts every entry’s `required_for_submission` flag. A manifest containing only those two passing gates is accepted with `overall_submission_ready: true`, `overall_decision: go`, and no blockers; retaining a blocker but changing its required flag to false has the same effect.

Freeze a canonical gate set and required/optional classification, then validate `go_no_go.new_confirmatory_outcomes`, claim promotion, and blocker lists against it. Regression tests should prove that deleting a mandatory gate or making `historical_empirical_replayability` optional fails. `.github/workflows/tests.yml:24` runs without `--require-ready`, so a green job means only that this incomplete structural check passed, not that submission gates passed.

## E19/E20 claim evidence is detached from the verified archive — High (**confirmed**)

`validate_claim_set` applies only `_require_sha256` to the four evidence digests (`scripts/check_submission_readiness.py:151-169`); it never loads `paper/artifacts/provenance_manifest.json` or compares archive roots, digests, counts, classes, or verdicts. Replacing E19’s manifest digest with any other lowercase 64-hex string still validates. CI runs this checker and the release verifier consecutively (`.github/workflows/tests.yml:24-25`) without linking their outputs, so unrelated but internally valid evidence descriptions pass together.

The validator also ignores `historical_source_limitation`, accepting its deletion or a contradictory `reconstruction_possible_from_digest: true`. Cross-check both studies against the central manifest and verified archives, including the false snapshot/reconstructibility flags and limitation semantics. Preserve the current truth: E19/E20 dirty source bytes are unavailable and cannot be recovered from their digests.

## Restricted evaluation acceptance is outside the verified contract — Medium (**confirmed**)

`verify_archive_manifest` checks `evaluation_acceptance.passed` only for boolean type and `accepted_primary_outputs` only for list shape (`verify_release_artifacts.py:426-445`). The outer verifier compares `passed` only with the `passed`/`failed` prefix of a free-form verdict (`verify_release_artifacts.py:529-535`); it never consumes the returned primary-output tuple or requires `passed` to agree with `checks`.

Bind each study to its permitted primary outputs and derive the pass bit from its declared required checks. Add semantic mutations with surrounding hashes updated; stale-hash tests do not show that a self-consistent but broadened or contradictory seal is rejected.

## `clean_git_source` is a syntactic assertion — Medium (**confirmed**)

`validate_source_provenance` accepts a 40-character lowercase string plus `git_dirty: false` and `source_reconstructible: true` (`verify_release_artifacts.py:213-259`) without proving that the object exists, is a commit, or hashes to `source_sha256`. `--require-git-tracked` checks only release files. `tests/test_release_artifacts.py:99-107` codifies the gap by accepting commit `bbbb…`, digest `aaaa…`, and no archived snapshot as `clean_git_source`.

Verify the Git object and executable-source fingerprint when Git is available. Offline verification should require an archived, hashed source snapshot or report the class as unverified rather than reconstructible.

## Provenance timestamp predates its indexed studies — Low (**likely**)

`paper/artifacts/provenance_manifest.json:3` says `generated_utc` is 2026-08-24, while the E19/E20 run IDs are dated 2026-08-25 (`:25-26`, `:94-95`). Unless the field intentionally denotes an earlier document version, regenerate it when finalizing the index or rename it to remove the current chronology conflict.
